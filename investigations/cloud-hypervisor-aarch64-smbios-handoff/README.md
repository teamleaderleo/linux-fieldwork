## TL;DR

Cloud Hypervisor already accepts SMBIOS-related `--platform` fields on AArch64, while conversion into the existing SMBIOS data model is compiled only for x86_64. The existing SMBIOS writer is largely architecture-independent; its x86-specific dependency is the fixed `SMBIOS_START` address.

Treat this as two changes with separate review decisions:

1. **Generation:** make the existing SMBIOS data model/writer usable from common code and plumb the already-parsed platform fields on AArch64.
2. **Firmware handoff:** decide how AArch64 UEFI obtains the generated bytes and installs them through the standard UEFI SMBIOS configuration-table path.

The current upstream proposal's fixed-address option is technically coherent and matches CloudHv's existing ACPI RSDP convention. The proposed **2 MiB** SMBIOS window has no format-level justification in the current writer: ordinary unit tests fit the complete table in a 4 KiB guest-memory range, and `setup_smbios()` returns the actual encoded byte count. A fixed handoff buffer therefore needs an explicit producer-size contract before its permanent guest-physical reservation is selected.

The strongest current recommendation is: **land or prototype common generation independently; keep the address/transport decision separate; derive a bounded handoff size from validated input limits instead of inheriting the 2 MiB FDT/ACPI granularity by analogy.**

## Explain like I'm five

Cloud Hypervisor already knows the guest's requested manufacturer, serial number, UUID, and OEM strings.

On x86 it turns those values into an SMBIOS table and places the table where firmware knows to look.

On AArch64 it keeps the values in configuration but never performs the final two steps.

There are two separate jobs:

```text
values -> SMBIOS bytes
SMBIOS bytes -> UEFI
```

The first job can reuse existing code. The second job needs a clear VMM/firmware agreement.

## Why care

AArch64 guests currently miss DMI/SMBIOS identity that the same Cloud Hypervisor configuration exposes on x86. Guest software can use manufacturer/product/OEM fields for platform detection and initialization.

The handoff choice also creates a long-lived compatibility contract between Cloud Hypervisor and its AArch64 firmware. A convenient address today can become guest-visible compatibility baggage later, especially if it moves the direct-kernel load address.

## Current source observations

### Platform configuration already accepts the data on AArch64

`vmm/src/vm_config.rs` defines these `PlatformConfig` fields without an architecture gate:

- `system_serial_number`
- `system_uuid`
- `oem_strings`
- `system_manufacturer`
- `system_product_name`
- `system_version`
- `system_family`
- `system_sku_number`
- `chassis_asset_tag`

The conversion method `PlatformConfig::smbios_config()` is under `#[cfg(target_arch = "x86_64")]` and returns `arch::x86_64::SmbiosConfig`.

That is the first exact owner: input parsing is already common; conversion and writer placement are x86-scoped.

### Existing writer is mostly common code

`arch/src/x86_64/smbios.rs` owns:

- the SMBIOS 3 entry point;
- Type 0 BIOS information;
- Type 1 system information;
- optional Type 3 chassis information;
- optional Type 11 OEM strings;
- end-of-table generation;
- UUID encoding and string-index checks;
- guest-memory write errors.

Its placement dependency is `crate::layout::SMBIOS_START`. The table payload starts immediately after the 24-byte SMBIOS 3 entry point.

This makes a common writer with a caller-provided start address, or a common writer plus architecture-specific placement wrapper, a natural first experiment.

### Current AArch64 low-RAM convention

At the pinned Cloud Hypervisor head:

```text
RAM_START       0x4000_0000
FDT_START       0x4000_0000
FDT_MAX_SIZE       0x20_0000
ACPI_START      0x4020_0000
ACPI_MAX_SIZE      0x20_0000
KERNEL_START    0x4040_0000
```

The upstream issue proposes:

```text
SMBIOS_START    0x4040_0000
SMBIOS_MAX_SIZE    0x20_0000
KERNEL_START    0x4060_0000
```

AArch64 `arch_memory_regions()` still describes the whole range from 1 GiB upward as RAM. FDT/ACPI/kernel placement is a boot-time convention layered inside that RAM range.

### A 2 MiB SMBIOS reservation is a policy choice

Current SMBIOS tests construct guest memory with a 4 KiB range at `SMBIOS_START` and successfully generate ordinary tables there. `setup_smbios()` returns the actual bytes used.

The proposed 2 MiB size therefore comes from mirroring the existing FDT/ACPI windows, not from the SMBIOS format or current encoder.

A smaller permanent buffer needs a maximum encoded-size rule. Current `PlatformConfig` accepts arbitrary Rust strings and an arbitrary OEM-string list; no nearby total-byte validation was found in this pass.

That input-limit question must be answered before choosing a tight fixed buffer.

## What AArch64 Linux actually consumes

Linux's current DMI scan checks the EFI configuration tables first when EFI config-table support is active. It prefers the SMBIOS 3 entry point and validates its signature, length, checksum, and table pointer before walking the table.

That matches the UEFI specification: SMBIOS and SMBIOS3 are standard EFI Configuration Table GUIDs. The stable guest-facing result is therefore the UEFI-installed SMBIOS entry, not the VMM-to-firmware bootstrap address itself.

No standard SMBIOS pointer property surfaced in the current Linux Devicetree binding search. A private FDT property would move the VMM/firmware agreement into another private ABI and would still require EDK2 code to install the UEFI configuration-table entry.

## Firmware-side evidence

### Current CloudHv AArch64 firmware

`ArmVirtPkg/ArmVirtCloudHv.dsc` already pins:

```text
system memory base       0x4000_0000
device tree initial base 0x4000_0000
ACPI RSDP base           0x4020_0000
```

It also configures SMBIOS entry-point production for the 64-bit SMBIOS 3 form.

The current platform does not use real QEMU fw_cfg for this path.

### Public fixed-address proposal

The inspected staging commit `56b39a...`:

- adds `SmbiosDxe` and `SmbiosPlatformDxe` to the AArch64 CloudHv firmware;
- keeps `QemuFwCfgLibNull`;
- introduces `PcdCloudHvSmbiosBaseAddress`;
- sets the AArch64 value to `0x40400000`;
- parameterizes the existing CloudHv SMBIOS reader so x86 can keep `0xf0000` while AArch64 uses its own PCD;
- sets the CloudHv host-bridge device ID used by the OVMF SMBIOS platform path.

This is a relatively small firmware change and cleanly reuses OVMF's existing CloudHv SMBIOS importer.

### Current OVMF importer

`OvmfPkg/SmbiosPlatformDxe/CloudHv.c` reads a SMBIOS 3 entry point from the CloudHv handoff address, checks the `_SM3_` anchor, and returns the entry point's table address. `SmbiosPlatformDxe` then feeds those records into EDK2's SMBIOS protocol, whose producer installs the standard EFI SMBIOS table for the guest OS.

So the fixed address is a bootstrap mailbox between VMM and firmware. It does not need to become the final SMBIOS table address seen by Linux after EDK2 imports the records.

## Option review

### Option A — fixed guest-physical handoff

Strengths:

- works with the default Cloud Hypervisor build;
- no new guest-visible fw_cfg device requirement;
- reuses the existing CloudHv OVMF importer;
- resembles the already-maintained fixed ACPI RSDP agreement;
- public firmware patch is small.

Open costs:

- creates another CloudHv VMM/firmware fixed-address contract;
- reserving space before the direct kernel moves `KERNEL_START`;
- the permanent size needs a producer bound;
- old firmware will simply miss a table written at the new address; new firmware with an old VMM sees no `_SM3_` entry there and therefore needs its empty/fallback behavior confirmed in execution.

### Option B — fw_cfg handoff

Cloud Hypervisor already contains an AArch64 fw_cfg MMIO implementation at the `0x09030000` device range.

Current product policy makes fw_cfg a compile-time optional feature. The CloudHv AArch64 firmware configuration currently uses the null fw_cfg library. Making SMBIOS depend on fw_cfg would therefore couple this identity feature to:

- enabling a currently optional VMM feature in the default/relevant build;
- exposing the fw_cfg device to the guest firmware;
- changing the CloudHv firmware configuration;
- defining the SMBIOS fw_cfg item behavior.

This can still be a good long-term channel if Cloud Hypervisor wants fw_cfg to become the common firmware mailbox. That is a broader product choice than the SMBIOS fix itself.

### Option A' — publish a pointer in FDT

FDT already exists on every AArch64 boot and EDK2 already parses it for several platform facts.

No standard Devicetree SMBIOS-pointer binding surfaced in this pass. A CloudHv-private property would trade a fixed address for a private DT property and parser. It also adds more firmware code than the current PCD proposal.

Keep this as a negative/control design unless a standard binding or existing EDK2 convention is found.

## Direct-kernel placement compatibility

Modern arm64 Linux boot documentation permits the Image to be placed at an appropriate aligned location in usable RAM; `0x40400000` is not a standardized mandatory kernel address.

Moving Cloud Hypervisor's direct-kernel placement still changes an observable boot convention. The candidate must therefore check:

- current direct-boot integration tests;
- older guest-kernel support claims, if any;
- payload loading and entry-point calculation;
- performance/test code that assumes the current address;
- snapshot/migration compatibility assumptions before treating the move as free.

Do not elevate a standards-permitted relocation into a compatibility claim until those local consumers are checked.

## First executable matrix

### Generation-only carrier

Build the existing SMBIOS writer from common code with architecture-specific placement supplied by the caller.

Controls:

1. x86 default table bytes stay identical;
2. x86 custom system/chassis/OEM fields stay identical;
3. AArch64 can construct the same table bytes into synthetic guest memory without firmware;
4. invalid UUID and guest-memory write failures stay typed errors.

This carrier should avoid changing AArch64 `KERNEL_START`, EDK2, or fw_cfg.

### Fixed-handoff carrier

After a size contract is selected:

| VMM | firmware | expected result |
|---|---|---|
| old | old | current empty/default AArch64 SMBIOS behavior |
| new | old | boot succeeds; new SMBIOS data may remain invisible |
| old | new | boot succeeds; firmware handles absent `_SM3_` handoff cleanly |
| new | new | configured manufacturer/UUID/OEM data appears under guest DMI |

Also run:

- UEFI boot with default SMBIOS data;
- UEFI boot with custom `system_manufacturer` and UUID;
- direct kernel boot before/after any `KERNEL_START` relocation;
- migration/snapshot only if source review shows the handoff address participates in saved compatibility state.

## Handoff-size discriminator

Before selecting a fixed `SMBIOS_MAX_SIZE`:

1. add explicit maximums for any unbounded producer dimension, or prove an existing parser maximum;
2. generate the largest accepted SMBIOS configuration;
3. measure encoded bytes including entry point and all record terminators;
4. choose a power-of-two/aligned reservation with explicit slack;
5. make overflow a typed configuration/build error rather than writing into the next boot payload region.

The separate Fieldwork investigation `cloud-hypervisor-smbios-oem-count` already found one producer-bound defect: Type 11's one-byte count can currently be truncated by an oversized OEM-string list. Fixing producer bounds is therefore useful independently of AArch64.

## Evidence boundary

Established:

- AArch64 parses the platform SMBIOS fields but has no `smbios_config()` conversion path;
- the current table writer is mostly independent of x86 except for placement;
- current AArch64 FDT/ACPI/kernel addresses are exactly mapped;
- AArch64 fw_cfg exists in Cloud Hypervisor but is compile-time optional;
- CloudHv AArch64 EDK2 currently uses a fixed ACPI RSDP PCD and the inspected SMBIOS proposal adds a fixed SMBIOS PCD while keeping fw_cfg null;
- Linux's EFI DMI path consumes the SMBIOS entry point from EFI configuration tables;
- a 2 MiB SMBIOS reservation is not required by the current encoder.

Open:

- selected fixed-buffer size;
- runtime new/old VMM/firmware compatibility matrix;
- exact impact of moving `KERNEL_START` on all supported direct-boot guests;
- whether Cloud Hypervisor maintainers prefer a broader fw_cfg policy change;
- candidate build/CI results.

## Stop condition

Choose a handoff design only when:

1. common generation has a small independently reviewable boundary;
2. producer size is explicitly bounded;
3. new/old firmware skew boots cleanly in both directions;
4. the selected transport reaches EDK2's SMBIOS protocol and guest Linux DMI with the configured values;
5. any direct-kernel address change passes its own compatibility checks;
6. the transport introduces no unrelated guest-visible requirement without an explicit design decision.

## Next safe action

Prototype the generation-only refactor first and add a maximum-size discriminator. In parallel, finish the Type 11 OEM-count boundary investigation. Defer the 0x40400000/2 MiB reservation decision until the encoder has an explicit maximum and the direct-boot address consumers are mapped.
