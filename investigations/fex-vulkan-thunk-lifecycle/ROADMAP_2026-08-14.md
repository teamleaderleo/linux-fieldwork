# FEX Vulkan investigation roadmap — 2026-08-14

This note keeps the active Vulkan work split into independently testable bug families. The goal is to avoid turning several real defects into one oversized candidate whose failures are hard to interpret.

## Lane 1 — callback / proc-address routing

Status: product candidate exists and is strongly validated on x86-64 guest / ARM64 host.

Clean candidate:

```text
repository: teamleaderleo/FEX
branch: fix/vulkan-callback-proc-routing
head: c011366706eaf65a00380003989b3a10811212b6
```

The candidate:

- adds the three missing dynamic custom routes:
  - `vkCreateDebugReportCallbackEXT`
  - `vkDestroyDebugReportCallbackEXT`
  - `vkCreateDebugUtilsMessengerEXT`
- makes native GIPA/GDPA availability authoritative before substituting a FEX custom implementation;
- preserves guest-callable GIPA/GDPA identity/self-query behavior.

Hosted ARM64 x86-64 runtime already covers direct and dynamic callback paths, disabled-extension NULL behavior, real-device GDPA, repeated lookup stability, and a dynamically obtained `vkCreateInstance` call.

### 32-bit boundary

A true i386 runtime probe of the exact clean candidate was attempted. The candidate and 32-bit probes compiled, but FEX never executed the test because the normal install contained no 32-bit Vulkan guest thunk.

That is current FEX build intent, not a missing rootfs package: `ThunkLibs/GuestLibs/CMakeLists.txt` puts Vulkan guest-thunk generation inside the `BITNESS == 64` block. The build produces a 32-bit Vulkan **host** thunk, but no standalone `GuestThunks_32/libvulkan-guest.so` Linux guest DSO.

Therefore current 32-bit coverage for this lane is:

```text
source inventory: covered
generator metadata/output: covered
32-bit host thunk compile: covered
standalone Linux Vulkan guest runtime: not a current built target
```

Do not report the i386 harness attempts as product failures. Reopen runtime coverage only if FEX begins building a 32-bit Linux Vulkan guest DSO or another supported 32-bit Vulkan guest path is identified.

## Lane 2 — preventing custom-route drift

Status: two viable prevention approaches are validated.

### Smaller incremental option

The existing prevention candidate mechanically compares the handwritten Vulkan lookup inventory against `custom_host_impl` metadata for both x86-64 and x86-32. It is narrow and easy to review.

### Generated-ownership option

The stronger experiment makes the thunk generator emit the internal custom-host registry from the same `custom_host_impl` metadata that declares the custom implementation.

Validated results:

- full FEX build passes;
- both 64-bit and 32-bit Vulkan host thunks compile;
- the generated registry contains the expected custom-host functions;
- top-level GIPA/GDPA stay outside the internal custom registry;
- the combined x86-64 ARM64 runtime matrix passes;
- focused `.ThunkGen` regression passes with all 16 generator tests green;
- an independent successor-function experiment (`vkDestroyInstance`) reproduces the same drift class when a new custom wrapper is added but the handwritten dynamic lookup is not updated.

The successor matrix is especially useful:

```text
native=0
native_dynamic=0
fex_direct=10
fex_dynamic=132
```

The new direct custom destroy wrapper returns safely (exit 10 is the probe's deliberate fidelity failure because callbacks were ignored), while GIPA bypasses that wrapper and re-opens SIGILL/132. This is direct evidence that dynamic registration must follow the custom declaration automatically or be protected by a strict invariant.

Canonical receipt:

```text
GENERATED_CUSTOM_ROUTE_REGISTRY_EXPERIMENT_2026-08-14.md
```

Decision is now review-scope/maintenance policy rather than feasibility. Generated ownership provides the stronger invariant but changes generic generator output; the inventory test is the smaller product change.

## Lane 3 — `vkCreateInstance` pNext callback mediation

Status: runtime-demonstrated adjacent callback escape and clean experimental repair.

The clean experiment does not delete the debug-utils create-info. It keeps the record and replaces only the guest callback with FEX's existing ARM-safe dummy callback.

The pNext walker also re-examines the newly linked node after removing a debug-report create-info. This closes the adjacent chain case:

```text
debug-report -> debug-utils -> ...
```

Combined ARM64 receipt:

```text
PNEXT_ZERO_CREATE result=0 callback_count=0
PNEXT_ADJACENT_CREATE result=0 report_count=0 utils_count=0
```

This should remain separable from the dynamic proc-address fix because it is a distinct callback escape during `vkCreateInstance` traversal.

A source branch `fix/vulkan-instance-callback-pnext` exists from the reviewed base, but no fix commit should be assumed on that branch until it is explicitly packaged and revalidated.

## Lane 4 — `VkAllocationCallbacks`

Status: separate runtime-demonstrated bug family; exact API scope is now machine-inventoried; product policy remains unresolved.

FEX treats `VkAllocationCallbacks` as opaque while it contains guest function pointers. Existing Vulkan wrappers apply inconsistent policies.

Exact audit against the pinned headers and reviewed interface:

```text
allocator-taking Vulkan commands: 133
custom_host_impl allocator commands: 8
generic allocator commands: 125
custom/generic paired asymmetries: 4
```

The exact four asymmetries are:

- Create/DestroyInstance
- Create/DestroyDevice
- Create/DestroyShaderModule
- Create/DestroyDebugUtilsMessengerEXT

Direct runtime evidence covers:

1. representative generic allocator escape (`vkCreateBuffer`);
2. instance create/destroy asymmetry;
3. consistent NULL suppression as a safe but semantically lossy mechanism;
4. dynamic GIPA bypass of a newly custom safe `vkDestroyInstance` wrapper when registration is omitted.

For the original instance pair, a native-valid allocator is honored on native ARM64. Under FEX, create succeeds with zero guest allocator callbacks because FEX substitutes NULL, then generic destroy with the same guest allocator dies before returning.

With a custom destroy wrapper that also passes NULL, direct destroy returns safely but the guest allocator remains ignored:

```text
fex_direct=10
```

The same new custom function obtained through GIPA bypasses the wrapper and dies again:

```text
fex_dynamic=132
```

Canonical receipt:

```text
ALLOCATION_CALLBACK_SURFACE_AUDIT_2026-08-14.md
```

Long-term policy choices remain:

1. full cross-ISA callback mediation;
2. consistent suppression where semantic loss is accepted;
3. explicit rejection/diagnosis of unsupported non-NULL allocators.

Next useful work is policy-oriented, not another near-identical Vulkan object pair. Check how existing FEX thunk libraries handle callback-bearing parameters that cannot be forwarded directly, then choose a Vulkan policy that fits project precedent.

Do not fold this bug family into the callback/proc-address candidate merely because both involve function pointers.

## Lane 5 — guest Vulkan thunk unload / reload lifetime

Status: independent Finding B with real generated-thunk runtime evidence.

This lane concerns stale dynamic-PFN/CustomIR state and executable guest-thunk lifetime across unload/reload. It is not the same failure as callback routing or allocation callbacks.

Existing Fieldwork receipts include the real Vulkan PFN lifetime A/B, exact FEX-2608 reproduction, in-flight execution race, and resident-bridge experiments.

Do not combine a lifetime/reclamation design change with callback routing unless an end-to-end test proves an unavoidable dependency. So far the evidence supports keeping them separate.

## Candidate boundaries

A reviewable progression should remain roughly:

```text
A. callback/procaddr runtime correctness
B. callback pNext mediation
C. registration-drift prevention
D. allocator policy work
E. thunk lifetime/reclamation work
```

A/B/C may eventually be adjacent commits if maintainers prefer, but each must retain its own regression evidence. D and E should stay separate until their project-wide policies are resolved.

## Reopen conditions

Reopen this roadmap if:

- FEX adds a supported 32-bit Linux Vulkan guest thunk or another real i386 Vulkan guest route becomes available;
- allocator policy work identifies an existing project convention that changes the suppression/mediation/rejection decision;
- a concrete API intentionally needs custom direct calls but native dynamic calls, invalidating generated registry ownership;
- upstream source changes alter the custom-host inventory or pNext handling;
- lifetime work proves a required dependency on callback/procaddr changes rather than an independent teardown defect.

No upstream FEX issue, PR, comment, reaction, or source mutation was performed by this investigation lane.
