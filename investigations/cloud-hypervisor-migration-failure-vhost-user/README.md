# Cloud Hypervisor — failed migration vhost-user recovery

Updated: 2026-08-11
State: SCOPING / SOURCE BOUNDARY MAPPED
Owning issue: #584
Exact upstream source: `cloud-hypervisor/cloud-hypervisor@915d359f97475b1a39d8561f8db514da9e692d19`
External-contact state: false; none occurred

## TL;DR

A source-side vhost-user backend can be intentionally shut down during migration snapshot, after which a later migration error can route through generic source-VM resume without recreating that backend.

The migration framework has `start_migration()` and `complete_migration()` hooks but no cancellation/rollback hook. `VhostUserCommon::snapshot()` uses `migration_started` to make snapshot destructive: it captures dirty state, joins vhost-user workers, and drops the backend handle. `Vmm::check_migration()` later handles any migration error by resuming the VM and returning it to normal VMM ownership.

`VhostUserCommon::resume()` is not a reconnect path. It signals an existing resume event and interrupts queues; it does not rebuild `self.vu` or respawn the worker that snapshot shutdown joined.

The first executable discriminator is a virtio-fs migration failed after snapshot but before final completion, followed by guest I/O on the recovered source.

## Explain like I'm five

To hand a vhost-user device to the destination, Cloud Hypervisor closes the source's connection after saving the device state.

That is useful when migration succeeds. If migration fails afterward, Cloud Hypervisor wakes the source VM again, but the generic wake-up path does not reopen the device connection that migration snapshot deliberately closed.

## Why care

A migration failure should return a usable source VM, not only a VM whose CPU state says `Running`.

Vhost-user devices include storage, filesystem, network, and generic backends. A source VM resumed with one of those backend connections gone can have guest-visible device failure even though migration recovery itself reports success.

## Intent and precedent

Upstream commit `68691db37bc6b133e0cf068137223daa75dad71a` changed vhost-user shutdown so paused epoll threads are resumed and joined, explicitly to close the backend connection after state capture and allow same-host/local migration.

The commit rationale says that after getting device state the vhost-user backend should no longer be used. That is a success-path handoff assumption.

A later migration failure invalidates the assumption because the source VM becomes authoritative again.

## Shared migration contract

`vm-migration::Migratable` currently provides:

```text
start_dirty_log()
stop_dirty_log()
dirty_log()
start_migration()
complete_migration()
```

There is no `cancel_migration()` or rollback callback.

`Vmm::send_migration()` calls `vm.start_migration()` for ordinary migration before the memory/snapshot phase. It calls `vm.complete_migration()` only after all later transfer/completion work has succeeded.

`Vmm::check_migration()` handles `Err` without a component migration rollback hook.

## Vhost-user lifecycle

`VhostUserCommon` carries:

```text
migration_started: bool
vu: Option<Arc<Mutex<VhostUserHandle>>>
```

`start_migration()` sets `migration_started = true`.

`snapshot()`:

```text
snapshot = serialize state
if migration_started {
    if dirty_logging {
        saved_dirty_log = dirty_log()
    }
    shutdown()
}
```

`shutdown()`:

- waits for vhost-user epoll workers so their backend-handle `Arc`s drop;
- removes the server socket path when relevant;
- sets `self.vu = None`.

This shutdown is deliberate and irreversible through ordinary `resume()`.

`complete_migration()` also clears migration flags, signals worker exit if present, and drops the backend handle. That is success-only cleanup.

## Failed migration recovery

The worker can still fail after `vm.snapshot()`, for example during:

- final dirty-memory transfer generated by snapshot side effects;
- `send_state()`;
- Complete/CompletePaused request or acknowledgement;
- dirty-log stop;
- postcopy drain;
- component completion.

`Vmm::check_migration()` then does:

```text
if source was Running and current state is Paused {
    vm.resume()
}
vm.stop_dirty_log()
self.vm = Owned(vm)
```

No component migration rollback occurs before resume.

## Why vhost-user resume does not restore the backend

`VhostUserCommon::resume()` calls `resume_internal()` and then triggers queue interrupts.

`resume_internal()` only writes to `resume_evt` when one exists. It does not:

- recreate a `VhostUserHandle`;
- reconnect to the backend socket;
- restore `self.vu` from `None`;
- recreate the epoll worker joined by `shutdown()`.

A successful eventfd write can therefore make the generic device resume call look successful even though no worker remains to consume it.

## First executable discriminator

Prefer virtio-fs because upstream already has live-migration coverage and its backend connection is easy to observe.

1. Boot source VM with migratable virtio-fs and prove guest filesystem access.
2. Start ordinary migration (`preserve_source=false`).
3. Advance through snapshot/state capture so source vhost-user shutdown occurs.
4. Fail a later protocol step before migration success.
5. Wait for `migration-failed` and source recovery.
6. Confirm VM state is Running.
7. Exercise the mounted virtio-fs path in the guest.
8. Inspect backend socket connection and Cloud Hypervisor worker state.

Expected source-derived result:

```text
before migration: backend connected; guest I/O works
after snapshot: source backend connection intentionally closed
late migration failure: source generic resume succeeds
post-recovery: backend not recreated; guest device operation fails/stalls
```

## Negative controls

- Fail before snapshot: vhost-user backend should not have been destructively shut down.
- `preserve_source=true`: `start_migration()` is skipped, so snapshot should not use the destructive migration path.
- Successful migration: source teardown and destination backend connection are expected.

## Candidate boundary

Required invariant:

> A component whose migration preparation/snapshot destroys source-side runtime state must have a defined rollback path before a failed migration resumes the source VM.

Potential designs after reproduction:

1. add a `cancel_migration()`/`rollback_migration()` hook to `Migratable` and implement source recovery for vhost-user;
2. add a vhost-user reconnect/reactivation method and call it during failed-migration recovery before `vm.resume()`;
3. move irreversible vhost-user shutdown later, only if backend ownership and same-host migration permit it.

Before choosing a generic trait change, inventory other non-default `start_migration()` implementations for destructive state.

## Adjacent contexts

### vhost-user net

Its `start_migration()` first invalidates announcement state, then delegates to the shared `VhostUserCommon` hook. Failed migration may therefore require both backend reconnection and announcement-state recovery.

### vhost-user fs/block/generic

They share `VhostUserCommon`; determine which configurations currently advertise/require backend migration state and choose the smallest supported runtime fixture.

### vDPA/VFIO

These have separate migration hooks. Review their failure semantics before making rollback generic.

### Disk locks

The same late-failure window can also resume the source without reacquiring advisory disk locks. That independent finding is tracked by #583.

## Results

Established by source/history review:

- ordinary migration sets vhost-user `migration_started`;
- vhost-user migration snapshot intentionally shuts down workers and drops the backend handle;
- migration can fail after snapshot;
- generic failed-migration recovery resumes the VM;
- vhost-user resume does not reconnect or recreate the killed worker/backend handle;
- the shared migration trait lacks a cancellation hook.
